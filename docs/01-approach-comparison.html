Claude Code 狀態燈：架構方案比較

把 SidePulse 的硬體體驗做成純軟體的 macOS menu bar app。這份文件比較三種狀態來源機制，並提出推薦方案。

一、已鎖定的需求

核心定位多 session 聚合儀表板
分發目標按開源標準寫，先自用跑起來
互動深度只看（read-only 狀態燈）

推論出的三條硬約束：(1) 不寫死路徑、hook 安裝必須可逆且不破壞使用者現有設定；(2) 不受 App Sandbox 限制，可自由讀 ~/.claude/；(3) 不需要雙向通道 —— 事件單向流入即可，架構可以很乾淨。

二、核心技術問題

Hook 給的是「狀態轉移」，我們要的是「當前狀態」。這個落差製造三個必須處理的失效模式：

  • 殘留狀態（stale）：terminal 被強制關掉 → SessionEnd 永遠不會來 → 那個 session 永遠卡在 working。
  • App 沒開時的事件：hook 照樣觸發但沒人接 → app 啟動後對現況一無所知，明明有 3 個 session 在跑卻顯示「無」。
  • 絕不可拖慢 agent：每個 tool call 都會觸發 hook。同步 hook 會直接卡住 Claude Code。

三、三種方案

方案 1 —— Claude Code Plugin + 單檔狀態信箱 推薦

關鍵洞見（讓這個方案變得極簡的原因）：狀態幾乎是「最後一個事件」的純函數 —— state = f(last_event)。所以不需要 event log、不需要 replay、不需要處理亂序。每個 session 一個檔案，直接覆寫，最後寫的贏。App 啟動時掃一次目錄就有正確現況。

安裝方式走 Claude Code plugin：plugin 自帶 hooks/hooks.json，用 /plugin install / uninstall 管理 —— 完全不用手改 ~/.claude/settings.json，天生可逆、天生不破壞使用者現有 hooks。這比 SidePulse 直接改 settings.json 乾淨。

方案 2 —— Local HTTP hook 直打 app

方案 3 —— Zero-config：直接觀測 transcript 與 process

推薦

方案 1 為主，把「事件來源」抽成 interface，讓方案 3 之後能當 fallback 補上。

理由：方案 1 在「不拖慢 agent」、「狀態落地」、「等待精準度」三個最重要的判準上同時最強，而且是唯一實作複雜度最低的。方案 2 唯一贏的是延遲，但 loopback 往返和 2ms process spawn 對「人眼看 menu bar」這個場景毫無差別 —— 拿永久遺失事件去換使用者感知不到的延遲，不划算。方案 3 的價值在「零安裝就有基本功能」和「之後接其他 agent」，所以留成 EventSource 的第二個實作，不進第一版。

六、Menu bar 視覺語言草案（動的，可以直接看）

聚合規則按「最緊急者優先」：error > waiting > working > done > idle。也就是說只要有任何一個 session 在等你，整條燈就是橘的。

working3 sessions 在跑，沒人需要你
waiting有 session 卡在權限請求 / 提問 — 最重要的狀態
done全部收工，且你還沒看過
errorStopFailure / tool 失敗
idle沒有活著的 session

已知的 macOS 約束：menu bar item 寬度要克制（8 顆 LED 大約 40pt 還可以）；動畫在螢幕睡眠 / menu bar 被遮住時必須停掉省電；必須跟隨深淺色，並尊重系統的「減少動態效果」設定（這份文件本身已經照做了）。
