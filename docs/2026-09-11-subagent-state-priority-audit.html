0. 結論先講

你的觀察是對的，而且不只一個成因。我找到 五個會讓「燈號」與「畫面實際狀況」對不上的路徑，其中兩個是真的 bug，一個是呈現層的殘影，兩個是設計上的必然（但可以講清楚）。

#你看到的真正的原因目前行為嚴重度
A 綠燈，但其實沒有結果可看 主 agent 講完話送 Stop 時，背景還在跑的具名 subagent 事件全部被丟掉 綠燈（done）。若該 session 同時也結束了（terminal 收掉），它還會進入「已結束未確認」尾巴，被面板確認後連檔一起刪 高
B 綠燈，但其實有人在等你批准 同一條 guard：subagent 的 PermissionRequest 在主槽靜止時也被丟掉 永遠不會變橘，直到你自己去看 高
C 面板副行寫著「implementer → Bash」，那個 subagent 早就結束了 SubagentStop 被映射成 .working；sub 槽只有主槽 done／error 才清 停在最後一個 tool 名不動 中
D 橘燈，但你早就按過 Allow 了 平台在「批准」的瞬間不送任何事件；下一個事件是 tool 跑完後的 PostToolUse 整段 tool 執行期間都是橘的 中
E 橘燈，但這個視窗沒事 一顆聚合燈涵蓋所有視窗，橘色屬於另一個 session 面板分得出來，燈分不出來 設計如此

1. 目前的模型

每個 session 的狀態檔有兩個槽：主槽與從屬槽。燈號取兩槽的優先序最大值。

effectiveActivity = max(mainActivity, subActivity ?? .idle)
優先序：error(4) > waiting(3) > working(2) > done(1) > idle(0)

寫入規則（Sources/AuraCore/MergeRules.swift）有兩條關鍵的：

// ① 主槽靜止（waiting / done / error）時，所有 subagent 事件一律忽略
guard !s.mainActivity.isQuiescent else { break }

// ② 主槽走到 done 或 error 時，清空整個從屬槽
if a == .done || a == .error { clearSubSlot(&s) }

主 agent 事件之後抵達的 SubagentStop延遲agent_type

所以 guard ① 本身有正當理由：沒有它，每個跑完的 session 過幾秒到三分鐘就會從綠燈跳回工作中，而且回不去。問題不在它存在，在它的適用範圍。

2.2 具名 subagent 的 payload 形狀 今天 21:30 實測

我掛了一個獨立的探針 plugin（不碰 repo、不碰 settings.json），跑一個真的 claude -p session 派 subagent，抓到：

0.00s  SubagentStart  agent_id='a0b503d0b03dbd023'  agent_type='general-purpose'
4.04s  SubagentStop   agent_id='a0b503d0b03dbd023'  agent_type='general-purpose'
5.52s  Stop           agent_id=None                 agent_type=None

這是修法的關鍵前提，而且成立：具名 subagent 的 SubagentStart 與 SubagentStop 都帶同一個 agent_id，也都帶非空的 agent_type。內部 subagent 的 agent_type 是空字串（已在 HookPayload 正規化成 nil）。
「具名」與「內部」在資料層分得開，而且結束事件配得回開始事件。

順帶量到的：SubagentStop 還帶 last_assistant_message（subagent 自己的結論）與 agent_transcript_path。目前完全沒用到 —— 面板其實有機會顯示「subagent 回報了什麼」，但那是另一個題目。

3. A 與 B：guard 的適用範圍開太大

guard ① 是用內部 subagent 的證據寫出來的，但它套用在所有 subagent 事件上。於是：

A：主 agent 講完話了，但它派出去的 agent 還在跑。燈說「有結果可看」，你去看卻什麼都沒有 —— 真正的工作還在背景。

B：更糟的一格。背景 subagent 撞到需要批准的 tool，送出 PermissionRequest（帶 agent_id），guard 把它丟掉。燈是綠的，實際上有人卡著等你。這正好是本產品最不該犯的錯的鏡像 —— 既有 invariant 防的是「不該橘卻橘」，這一格是「該橘卻不橘」。

為什麼現有測試沒抓到：三條相關的 gate（internalSubagentStopAfterStopIsIgnored、subagentStopAfterStopFailureIsIgnored、subagentIgnoredWhileWaiting）測的都是「靜止之後不該被改變」的方向。沒有任何一條測「靜止之後真的還有事在跑時該怎樣」 —— 那個情境從來沒有被寫成測試，因為 spec 也沒寫。這是 CLAUDE.md 講的「gates share one eye」：四道關卡都從同一份假設出發。

4. C：從屬槽的殘影

SubagentStop 在 EventMapping 裡對應 .setActivity(.working)。對主槽而言那是對的（subagent 回來了，主 agent 繼續工作），但同一個映射被拿去寫從屬槽，語意就反了 —— 「這個 subagent 結束了」被記成「這個 subagent 正在工作」。

加上 subTool／subAgentType 都是 carry-forward，結果是：subagent 結束後，面板副行會一直掛著它最後一次用的 tool，直到主 agent 走到 done／error 才清掉。你看到的「沒有任何反應」有一部分就是這個殘影。

5. D：橘燈的另一個成因，與 subagent 無關

實測序列（round2，同一個 session）：

1215.18s  PreToolUse         Bash
1215.18s  PermissionRequest  Bash     ← 主槽變 waiting，燈變橘
   （你按下 Allow —— 平台不送任何事件）
1223.16s  PostToolUse        Bash     ← 這時才變回 working

也就是說從你批准的那一刻到 tool 跑完，燈都是橘的。這裡是 8 秒，但如果批准的是 swift test，那就是兩分鐘的假橘燈。

這個修不掉（在目前的平台契約下）。「批准」沒有對應的 hook event —— Elicitation 有 ElicitationResult 收尾，PermissionRequest 卻沒有對應的 PermissionGranted。唯一的辦法是時間衰減，而那違反本專案「不做 time-based gate」的教訓，也會在你真的離開時說謊。
實務影響有限：你多數時間跑 bypassPermissions，這格根本不會出現。建議記成 known gap。

6. 提案

6.1 核心：把「還有幾個具名 subagent 在外面」變成一個真的狀態

不要再用「主槽靜止就全丟」這條粗規則。改成記錄在外面的具名 subagent 集合，用 agent_id 當 key：

outstandingSubagents: [agentID: (type, tool)]

• 任何帶 agent_type（非空）的 subagent 事件  → upsert
• SubagentStop 且 agent_id 在集合裡          → remove
• UserPromptSubmit（新一輪）                  → 清空（保險）
• 內部 subagent（agent_type 空）              → 從不進集合，它的遲到 Stop 自然是 no-op

然後燈號多吃一個輸入：

effectiveActivity = max(mainActivity,
                        subActivity ?? .idle,
                        outstandingSubagents.isEmpty ? .idle : .working)

為什麼這個形狀是對的深度：§2.5.1 當初真正想擋的是「內部 subagent 的遲到事件」。現在用 agent_type 直接把內部 subagent 排除在集合之外 —— 用資料本身的區別去擋，而不是用「主槽的狀態」去猜。原本那條 guard 是拿相關性當因果。

6.2 B（等待決策）要單獨處理

具名 subagent 的 PermissionRequest／Elicitation 必須能把燈變橘，即使主槽已經 done。做法：集合裡的項目帶自己的 activity，第三個輸入取集合內的 max，而不是固定 .working。

6.3 C（殘影）：SubagentStop 在從屬槽的語意改成「移除」

不是改 EventMapping 的回傳值（主槽仍然需要 .working），而是在 MergeRules 的 sub 分支裡對 SubagentStop 特判成清除。

6.4 哪些既有 gate 會受影響

測試提案後說明
internalSubagentStopAfterStopIsIgnored維持綠agent_type="" → 從不進集合 → done 仍是 done
subagentStopAfterStopFailureIsIgnored維持綠SubagentStop 只會移除、不會新增
subagentIgnoredWhileWaiting維持綠斷言的是 subActivity == nil；集合是另一個欄位，不碰它
subagentCannotMaskWaiting維持綠max(waiting, working) 仍是 waiting
stopClearsSubSlot維持綠從屬槽照清；集合是獨立的

一條既有測試都不用改。這是刻意的設計 —— 不動既有斷言就不會有「弱化 vs 對齊」的爭議。新行為由新 gate 覆蓋。

實測驗證這個判斷（2026-09-11 晚）：我把「最直覺的修法」套上去試——只是在 guard 上開個口讓具名 subagent 通過：

guard !s.mainActivity.isQuiescent || p.agentType != nil else { break }

結果：落差 A 與 B 的釘樁測試如預期變紅（0.004 秒），但同時打斷三條既有 gate —— subagentCannotMaskWaiting、subagentIgnoredWhileWaiting、subagentStopAfterStopFailureIsIgnored， 全都是因為它開始往 subActivity 寫東西。
所以「直覺修法」是不能用的，而上面那張表所依據的設計（另開一個集合、完全不碰從屬槽）不是紙上談兵，是被這次 mutation 反證出來的唯一安全形狀。

6.5 新 gate（各自要有 mutation）

  • 主 agent Stop 後，具名 subagent 仍在跑 → 燈必須是 working，不是 done。mutation：拿掉第三個輸入 → 必紅
  • 該具名 subagent 的 SubagentStop 抵達 → 燈回到 done。mutation：remove 改成 no-op → 必紅（燈卡住）
  • 主槽 done 時具名 subagent 送 PermissionRequest → 燈必須橘。mutation：集合固定回 .working → 必紅
  • 內部 subagent（agent_type=""）的遲到 SubagentStop → 燈維持 done。用 round2 的真實 payload，不是手搓的
  • 具名 subagent 結束後，面板副行不得再顯示它的 tool。

7. 風險與還沒量到的東西

項目狀態如果猜錯會怎樣
具名 SubagentStop 帶 agent_id 與 agent_type已量測—
subagent 崩潰時是否仍送 SubagentStop未量測集合永遠不空 → 燈卡在 working。
保險：UserPromptSubmit 清空集合，最多髒一輪
agent team（多個並行 agent）的 agent_id 是否各自獨立未量測集合設計本來就以 id 為 key，多個並行是自然支援；但需要一次真的 team 派發來確認
subagent 內再派 subagent（巢狀）未量測目前無證據顯示會發生；集合不會爆，最多多一筆

8. 不做的事

  • 不改 D1 優先序本身（error > waiting > working > done > idle）。五個狀態的相對關係沒有問題，問題在「有沒有正確地知道自己處在哪一個狀態」。
  • 不加時間衰減／TTL。本專案已經被 time-based gate 咬過兩次。
  • 不把 idle_prompt 拿來當 waiting 的收尾（既有 invariant，會讓每個講完話的 session 亮橘）。
  • 不動聚合成一顆燈這件事（E）。面板已經分得出是哪個 session。
