2 · 三個只有實測才找得到的 bug

設計階段實際跑了 141 個真實 hook payload。以下三件事讀文件讀不出來， 而每一個都會讓產品在最關鍵的時刻失效。

① subagent 事件會抹掉主 agent 的 waiting

單槽 last-write-wins 的話，主 agent 正在等你批准時，一個 subagent 的 PreToolUse 會把狀態蓋成 working —— 橘燈消失，而你根本不知道它在等你。

修法：主／副分槽 + 取優先序最大值；主槽處於靜止態時完全忽略 subagent 事件。

② 使用者按 Deny 不產生任何 hook 事件

實測序列：PermissionRequest → （按 Deny）→ 什麼都沒有 → SessionEnd。 所以 waiting 絕不能進入「已結束但未確認」的尾巴，否則一個你早就回答過的 session 會讓 icon 一直亮橘燈說「有人在等你」。

③ PostToolUseFailure 的錯誤欄位叫 error，不是 tool_error

我一開始寫進 spec 的結論是「它沒有錯誤欄位」。那是因為我透過一份自己寫的 key 過濾器 去看 payload，而那份過濾器不含真正的欄位名。

用自己的假設去觀察，只會看到自己的假設。

3 · 這一輪真正的主題：空轉的守衛

18 個 task 之外跑了 10 輪修復批次。回頭看，絕大多數 finding 都是同一族—— 一個看起來像守衛的東西，實際上永遠不會觸發，於是測試照樣全綠。

空轉的守衛比沒有守衛更糟，因為它製造信心。
#形狀本專案的實例
1取樣掏空覆蓋 i % 8 == 0 讓 9 個型別真的會讀的欄位零損壞測試， 包括那個 commit 自己新增的兩個
2>= 代替 == checked.count >= 12 無法察覺整批遺漏
3測資位置讓 mutation 隱形 [working, working, error] —— error 剛好在最後， 「最後一個贏」的錯誤實作巧合給出正確答案
4假逾時 timeout: 5 的檢查點在「收到元素之後」，零元素時永久 block —— mutation 下掛住而不是變紅
5拿被測物當終止條件 靠「stop() 會 finish() stream」來結束迴圈，而那正是被測的性質
6守衛從未被觸及 allSessionIDs 有三個過濾條件，樣本只觸及一個
7零樣本恆綠 for 迴圈跑零次時，裡面的斷言一次都不執行
8宣稱沒有被檢查 doc-comment 說「涵蓋每一個 stored property」，但那句話本身沒有被斷言 —— 實際漏了兩個欄位

共同的修法方向

不是「多加測試」，而是把宣稱變成從來源推導的斷言，或去問持有契約的那一方。

黑名單 → 白名單基準

隔離 gate 原本是黑名單 ["AppKit","SwiftUI","Cocoa"]。 改成在測試時算出基準線：編一個只 import Foundation 的 probe， 它載入的 module 集合就是那一層的閉包；被測 target 不得超出它。

實測：AuraCore 載入的 17 個 module 與基準一個不多一個不少。 而加一行 import CoreImage（不在黑名單上）—— 舊 gate 是綠的，新 gate 精準點名 6 個超出基準的 module。

基準隨工具鏈自動更新，所以升級 Swift 不會誤紅；而任何新框架都會超出基準。

4 · gate 的三種類型

最終 reviewer 把 8 條 plugin wired-gate 逐一分類，結果很有啟發性：

類型條數防得住什麼防不住什麼
內部一致性6drift 「我從頭到尾就理解錯了」
平台契約1理解錯—
存在性1產物沒建出來—

關鍵觀察：連「跨層 source-derived 雙向等式」這種真的抓到過 regression 的強 gate， 仍然是內部一致性 —— 如果兩邊犯了相同的錯，它看不出來。

而歷史正好印證：hooks.json 把事件放在最外層時（整個 plugin 的 hook 一個都不會載入）， 當時 7 條 gate 全部綠燈，因為沒有一條真正問過平台「你會不會載入這個 hook」。

每一個「tested ≠ wired」的風險點，至少要有一條會去問外部權威的 gate。 只有內部一致性的話，測試數量再多也只是把同一個誤解複製了很多份。

5 · 最終審查抓到的（都已修）

一位獨立 reviewer 在自己的 worktree 裡跑了全量測試 3 次、TSan 867 秒、獨立重量覆蓋率， 並自製 probe 測試。verdict：「不可直接合進 main —— 但只差一小步」。

Critical 回訪 session 的結果被靜默吞掉

acknowledged 從不回收。整夜 pipeline 失敗 → 早上開面板看過 → 下午 claude --resume 同一個 id 又失敗 → 紅燈從來沒亮過。

已修 兩條移除路徑都回收；三條 probe 在還原修法後全紅。

Critical 解析失敗被當成「檔案不存在」

aura-hook 若在 truncate 與 write 之間被 SIGKILL， 磁碟上留下永久損壞的檔 → 5 秒後一個真的在等你批准的 session 被移除 → 而你還沒回答，不會再有事件重建它 → 橘燈永久熄滅。

同一份規格，HookFileSource 做對了、PipelineGraph 做反了 —— 因為 read 用同一個 nil 表達兩種語意完全不同的失敗。 已修

Critical 整個 app 層零測試覆蓋

把 AppDelegate 的 graph.start() 與 liveness timer 整段註解掉 （產品開起來永遠什麼都不顯示），220/220 全綠。

這是整個專案從頭到尾在防的失效模式，出現在最後一層。 已修 補上 spec 要求的 composition-root smoke 後， 同一個 mutation 在 5s / 10s 內各自變紅（有界失敗，不是掛住）。

Important 面板說不出在等什麼

toolDescription 被完整解析、合併、落檔、有 round-trip 測試 —— 然後沒進 SessionState。面板顯示的是「等你批准：Bash」， 而那一字不差就是 HookPayload 的 doc-comment 自己判定「不夠」的那個字串。

四段資料流（payload → 檔案 → state → UI）每一段都有測試， 但第四段的測試直接手造 SessionState，繞過了第三段 —— 接縫因此隱形。已修 用 Mirror 從輸出端推導出第三段的 gate。

7 · 已知缺口

明確未實作的 spec 條目（不是「做了但不完美」，是沒做）：

  • §3.8 自我健檢（死 hook 偵測） —— R6 的後半。屬 M5，需另出計畫。 verify-install.sh 做的是安裝當下的一次性驗收，不是持續健檢。
  • §4 重繪節流 ≥100ms、面板列表虛擬化 —— spec 明文列出的兩項。

已實作但未驗收：

  • R5（形態用證據決定）尚未滿足。 spec 要求 M4 同時做兩個原型 （A：8 顆 LED 燈條；B：單一符號 + 顏色 + 動畫），由 persona-tester 對 餘光辨識與遠距辨識打分後選定。本分支只做了形態 A。 spec 的風險登記表明確寫著前一個同類專案就是失敗於形態選擇 —— 這一項不該被跳過。
  • 視覺呈現未經人眼驗收 —— 執行環境沒有螢幕錄製 / 輔助使用權限， 無法截圖或自動點擊。渲染判斷邏輯有 31 個純邏輯測試覆蓋，但「橘色呼吸看起來對不對、 餘光掃到會不會注意到」必須由人跑一次 open build/AgentAura.app 親眼確認。
  • LEDStripView 目前把 8 顆 LED 畫成相同顏色與 alpha，資訊量等於 1 顆。 IconAppearance 已帶著 liveCount / attentionCount， 要讓「亮幾顆」有意義只需幾行 —— 但那是形態決策，刻意留給 M4 的 A/B 一起測。
