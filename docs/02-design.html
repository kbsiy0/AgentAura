AgentAura · 設計討論 02

系統設計

方案 1（Claude Code plugin + 單檔狀態信箱 + Swift menu bar app）的完整設計。含前一版兩個 mapping bug 的修正。

修正 · 來自你的提問

Bug 1 — PostToolUseFailure → error 是錯的。一個 tool call 中途失敗是 agent 工作的正常組成（grep 沒命中、測試紅燈、型別檢查失敗），不該把燈變紅。紅色只保留給 StopFailure（整輪因 API 錯誤死掉）。修掉之後才成立一個關鍵性質：所有 waiting / done / error 都是靜止態 —— 後面不會再有事件蓋掉它們，所以「單檔覆寫、最後寫的贏」不會弄丟你需要看到的資訊。

Bug 2 — session 結束時，未被確認的 error / done 會憑空消失。整夜跑 pipeline、terminal 自己收掉，你早上回來看到的是暗燈 —— 這剛好殺掉這產品最大的價值。修法：session 進入靜止態時標成 unacknowledged，即使 SessionEnd 到了或 pid 死了，它仍然參與 icon 聚合，直到你打開面板才算確認。因為 scope 是「只看」，打開面板正好是唯一的互動，用它當確認手勢最自然。

本文件已被部分校正

2026-09-08 在機器上找到 33 個真實 hook payload，推翻了本文件數處建立在文件推測上的假設：面板顯示的模型欄位拿不到、effort 形狀不同、Notification 未知型別的 fallback 是錯的，並抓到一個 critical bug（subagent 會蓋掉主 agent 的 waiting）。校正詳見 設計討論 03；正典為 docs/superpowers/specs/2026-09-08-agentaura-design.md。

一、兩層狀態模型

把「單一 session 的狀態」和「icon 顏色」明確分成兩層，各有各的規則 —— 這是前一版沒講清楚的地方。

關鍵性質：waiting / done / error 三者之後在使用者行動前不會有新事件，所以「覆寫式單檔」不會弄丟它們。這是整個設計能這麼簡單的原因。

第 2 層：聚合優先級（已裁決）

error 和 waiting 誰優先，我認為值得你決定，因為兩者「急」的性質不同：

  • waiting —— agent 正被擋住，每一秒都在浪費你的 wall-clock。時間壓力高。
  • error —— 已經停了，沒有時間壓力，但比較觸目、你會想知道。

裁決結果：error > waiting > working > done > idle —— 紅色絕對優先，最不易錯過。（我原本建議 waiting 優先，讓「還能救的」贏；使用者選了 error 優先，這是產品判斷。）實作為 Activity enum 的 rawValue 順序 + 一條 mutation 驗證，面板排序同步跟進。

二、元件切分與介面

核心邏輯（AuraCore）完全不碰 AppKit，是純函數 + 純資料，可以在無 GUI 環境完整測試。AppKit 只出現在最外層的 renderer。

protocol EventSource {                        // 方案 1 = HookFileSource；方案 3 = TranscriptSource (v2)
    func bootstrap() throws -> [SessionSnapshot]     // app 啟動時掃目錄，還原現況
    var snapshots: AsyncStream<SessionSnapshot> { get }
}

enum Activity: Int, Comparable { case idle, done, working, waiting, error }   // rawValue 即優先序

struct SessionState {
    let id: String, projectPath: String, model: String?, permissionMode: String?
    let activity: Activity
    let currentTool: String?, turnStartedAt: Date?
    let subagents: [String: Int], toolFailures: Int
    let lastMessage: String?, errorType: String?
    let acknowledged: Bool
    let liveness: Liveness                      // .alive(pid_t) | .ended
}

protocol AggregatePolicy { func aggregate(_ s: [SessionState]) -> IconState }  // 純函數
protocol IconRenderer    { func render(_ s: IconState) }

三、資料契約

~/.agentaura/sessions/<session_id>.json —— 每個 session 一個檔，由 aura-hook 覆寫。

{
  "schema": 1,
  "session_id": "abc123",
  "hook_event_name": "PermissionRequest",
  "written_at": "2026-09-08T17:42:03.117Z",
  "pid": 48213,                    // hook 的 getppid() = claude 本體
  "pid_started_at": 1757352011,    // 防 pid 回收誤判
  "cwd": "/Users/you/Code/Vibe/AgentAura",
  "model": "claude-opus-5",
  "permission_mode": "default",
  "effort": "high",
  "tool_name": "Bash",
  "notification_type": null,
  "error_type": null,
  "last_message": null,
  // ↓ 累積欄位：aura-hook 在 flock 下 read-merge-write 帶過來
  "turn_started_at": "2026-09-08T17:41:12.004Z",
  "subagents": { "Explore": 2, "implementer": 1 },
  "tool_failures": 3
}

為什麼 aura-hook 要做 read-merge-write（而不是純覆寫）

面板要顯示「已跑多久」、「subagent 數量」、「tool 失敗次數」，這三個是累積量，不是最後事件的函數。兩個選擇：讓 app 在記憶體累積（app 重啟就歸零），或讓 helper 在檔案裡累積（永久正確）。選後者，因為你會整夜跑 pipeline，app 重啟後面板變空白是不能接受的。

競態安全靠 flock(LOCK_EX)。因為檔案是 per-session，跨 session 零競爭；同一 session 內事件近乎循序，overlap 極少 —— 但 async: true 理論上可能重疊，所以鎖是必要的，不是可選的。App 端讀取取 LOCK_SH，讀不到就重試（不能因為讀到半截 JSON 就當成沒有 session）。

六、測試策略

依 user CLAUDE.md Lessons Learned #1，T01 不含任何生產碼，只建對抗式測試底座。

T01-a · 對抗式 double（刻意回「樂於配合」的 fixture 不會回的東西）

  1. 截斷／半截 JSON（模擬讀到寫入中）
  2. pid 已死；pid 被回收成另一個啟動時戳更晚的 process
  3. 事件亂序落地（async 導致 Stop 比 PostToolUse 早寫入）
  4. 未知 hook_event_name、未知 notification_type、缺必要欄位、多出未知欄位
  5. 50 個 session 併發寫同一目錄
  6. emoji / unicode / 超長專案路徑；session_id 含 ../ 之類的 path traversal
  7. 時鐘倒退（turn_started_at 落在未來）
  8. 磁碟滿 / 目錄唯讀 → aura-hook 必須靜默成功

T01-b · composition-root smoke（測過的能力 ≠ 接線的能力）

  • 實跑 AppDelegate.buildGraph()，斷言 FSEvents watcher 真的訂閱到 ~/.agentaura/sessions
  • 斷言 StatusItemController 真的收到 IconState 更新（spy 斷言呼叫確實發生，不是被 catch-all 吞掉）
  • 斷言 plugin 的 hooks/hooks.json 裡的 command 路徑，指向 app bundle 內真實存在且可執行的 aura-hook —— 這是 tested≠wired 最經典的位置，路徑一錯整個產品靜默失效而所有單元測試照樣全綠
  • 端到端 wired-gate：用真的 aura-hook 二進位 + 真的檔案 + 真的 FSEvents，不 mock 任何一層，斷言 IconState 改變

Mutation 驗證（每個關鍵 gate 都做）

  • 撤掉 AggregatePolicy 的優先序 → 「2 working + 1 error 應為 error」必須 RED
  • 撤掉 unacked 尾巴保留 → 「session 結束後 error 仍計入」必須 RED
  • 把 PostToolUseFailure 改回 error → 「tool 失敗不改變 activity」必須 RED
  • 把 aura-hook 路徑改成不存在 → composition-root smoke 必須 RED

十、已裁決

  1. 聚合優先序 = error > waiting > working > done > idle
    使用者裁決（未採用我建議的 waiting 優先）：紅色絕對優先，最不易錯過。實作為 Activity enum 的 rawValue 順序 + 對應 mutation 測試。面板排序同步跟進。
  2. 看過面板即 acknowledge——在關閉時
    面板關閉瞬間（didClose），registry 中所有未確認 session 一律標為已確認（不論是否可見）。已結束且已確認者移出 registry 並刪檔。開啟時不動——否則已結束的列在畫出前就被移掉（2026-09-10 實測，S1-3）。
  3. 設計核准，已寫成 spec
    docs/superpowers/specs/2026-09-08-agentaura-design.md 為正典；本文件為討論呈現記錄。
