實測校正與 前一個專案 殘留

在機器上找到前一個同類專案 前一個專案 留下的 33 個真實 hook payload。它們回答了 spec §8 裡列的未驗證事項，抓到一個 critical bug，並暴露一個目前正在發生的問題。

正在發生 · 需要你決定

前一個專案 的 7 個 hook 還全部留在 ~/.claude/settings.json，但 app 已經不存在了。

$ ls /Applications/前一個專案.app
ls: No such file or directory

$ echo '{}' | /Applications/前一個專案.app/Contents/Resources/prior-hook hook
zsh: no such file or directory
exit=127

註冊在 SessionStart、UserPromptSubmit、PreToolUse、PostToolUse、Notification、Stop、SessionEnd 七個事件上，全部是同步 command hook（沒有 async: true）。也就是說這台機器上每一個 Claude Code session、每一次 tool call，都在同步 fork 一個不存在的執行檔然後拿到 exit 127。不會擋住 agent（127 ≠ 2），但每個 tool call 都白付一次 fork/exec。

settings.json.ORIGINAL（前一個專案 安裝前的備份）證實乾淨基線是完全沒有 hooks key —— 沒有需要保留的既有 hook。所以清理動作就是把整個 hooks 區塊移除。

這件事驗證了設計決策 D3

前一個專案 直接改 settings.json，app 被移除後 hook 就孤兒化了 —— 這正是 AgentAura 選擇走 Claude Code plugin 而非改 settings.json 的理由（spec §3.2）。/plugin uninstall 天生可逆，不可能留下指向已刪除執行檔的死 hook。原本這是紙上的論證，現在有你自己機器上的實證。

一、CRITICAL：subagent 會蓋掉主 agent 的 waiting

Subagent 的 tool 事件共用父 session 的 session_id，只靠 agent_id 區分（主 agent 為 null）。在單槽 last-write-wins 下，subagent 的事件會覆寫主 agent 的狀態。

下圖是實測資料裡的真實時序（session e69dc6d9）—— 主 agent 一個 Bash 跑了 19.47 秒，期間 subagent 插進 8 個事件：

修法

檔案裡分兩槽，session 的 activity 取兩者在既有優先序下的 max：

if payload.agent_id == nil { file.main_activity = activity(of: payload) }
else                       { file.sub_activity  = activity(of: payload) }

let activity = max(file.main_activity, file.sub_activity ?? .idle)

因為 waiting(3) > working(2)，max 天生保住 waiting。不新增任何機制 —— 純粹複用 D1 已裁決的優先序。附一條 mutation 驗證：改回單槽 → 對應測試必 RED。

二、一個必須避免的錯誤解讀

初次分析時我把兩個 log 檔合併、依時間排序，看到「SessionEnd 之後 11 秒還有事件」，一度判定為嚴重 bug（殭屍 session 復活）。

按 session_id 重新分組後證實是合併造成的假象 —— probe hook 是全域安裝的，兩個檔案裡混著兩個不同 session 的事件。單一 session（91a40169）的時序完全乾淨：

SessionStart → UserPromptSubmit → (PreToolUse/PostToolUse)* → Stop → SessionEnd
                                                    SessionEnd 之後：0 個事件 ✓

同一份資料裡，subagent 覆蓋主 agent 則是真的（§一）。教訓已寫進 spec §5.1 測試案例 11-12：跨 session 的資料一律先按 session_id 分組再看時序。

三、payload 契約校正（7 項）

前一版的欄位假設建立在文件推測上。實測後：

欄位文件／前一版假設實測結果
modelSessionStart 帶 model任何 event 都沒有
effort字串 "high"物件 {"level":"xhigh"}
SessionEnd 結束原因end_reason實際是 reason
SessionStart無額外欄位有 source（fresh / resume）
PostToolUse只有 tool_output有 duration_ms 與 tool_response
Stoplast_assistant_message確認存在；另有 background_tasks / session_crons / stop_hook_active
全部 tool event—皆帶 scratchpad_dir / prompt_id / transcript_path

影響：面板不能顯示模型（hook 完全拿不到）。transcript_path 出現在每個 payload 上，是唯一的 enrichment 縫，但那要依賴內部 jsonl 格式 —— 不進第一版。反過來拿到兩個沒預期的好東西：duration_ms（面板可顯示 tool 耗時）與 source（區分新開／resume）。

四、Notification 的 12 種型別 —— 我原本的 fallback 是錯的

前一版寫「未知 notification_type 一律 fallback 成 waiting，寧可誤報也不要漏掉在等你的」。這是錯的：未知空間裡佔多數的是雜訊。

notification_typeactivity
permission_prompt / idle_prompt / agent_needs_inputwaiting
elicitation_dialog / elicitation_url_dialogwaiting
agent_completeddone —— 不是 waiting
auth_success不改變
elicitation_complete / elicitation_response不改變
quota_auto_resume_fired / _stale / _disabled不改變
未知型別不改變（原本是 waiting）

改成「不改變」是安全的，理由：PermissionRequest 是獨立的 hook event，已經直接覆蓋「有人在等你」這個最重要的情況，不需要靠 Notification 兜底。照原本的寫法，auth_success 或 quota 自動續用都會讓 icon 無故亮橘。

注意：這 12 個型別的來源是 前一個專案 的 matcher 設定與官方文件 —— 從未捕獲過活的 Notification payload，連 notification_type 這個欄位名本身都未經量測。所以在 M0 補到真實 payload 之前，Notification 一律不改變 activity（fail-safe，讓 PermissionRequest 承擔）。

仍待實測的 3 個機制問題

  1. plugin 的 hooks/hooks.json 是否支援 async: true（前一個專案 走 settings.json，沒驗過 plugin 路徑）
  2. hook 子行程的 getppid() 是否等於 claude 本體的 pid（可能中間隔一層 shell）—— 這條若不成立，liveness 偵測整套失效
  3. ${CLAUDE_PLUGIN_ROOT} 在 plugin hook command 中的實際展開結果

已由實測回答（原本列在 spec §8）：payload 欄位集合、事件時序、PreToolUse 與權限提示的相對順序、subagent 共用 session_id 的行為、model 不存在、effort 形狀、SessionEnd 欄位名、hooks 改完立即生效不需重啟。
